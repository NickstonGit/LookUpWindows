# LookUp Windows

Небольшая Windows-утилита: выбираете несколько открытых окон — и видите их
**живые миниатюры** в плавающих окнах поверх всего экрана.

Живые превью получаются через Windows Desktop Window Manager
(`DwmRegisterThumbnail` / `DwmUpdateThumbnailProperties`) — без скриншотов и почти
без нагрузки на CPU.

Версия: **2026.10.05.1** (`APP_VERSION` в `src/config.py`).
Автор: **Nickston**

### Toggle исходного окна кликом по PiP

Клик по области превью работает по фактическому состоянию исходного окна:

- если source видим — LookUp паркует его практически за границей виртуального рабочего стола, не минимизируя; PiP остаётся live;
- если source уже припаркован LookUp — клик возвращает его в точное исходное положение/состояние и активирует;
- если окно было реально свернуто внешним действием — клик восстанавливает и активирует его;
- все парки фиксируются в журнале `restore` (`settings.json.park.json`) до перемещения окна: даже краш, `taskkill /f`, зависшее включение или целиком не отвечающее окно не оставят чужое окно вне экрана — следующий запуск восстановит окна из журнала;
- parked-source возвращается через проверяемый restore: состояние считается восстановленным только после фактического появления окна на экране; taskbar/Alt+Tab и случайное minimize parked-window также запускают recovery;
- пункт контекстного меню «Открыть окно» остаётся однозначным: он всегда возвращает/активирует окно и никогда не скрывает его.


## Возможности

- живые DWM-миниатюры выбранных окон (обновляются сами, без скриншотов);
- каждое превью — **отдельное плавающее окно (PIP)**: перетащите его за заголовок
  в любое место экрана — позиция запоминается;
- небольшое **окно управления**: «+» — добавить окно, «⚙» — настройки, «✕» — скрыть только панель;
  при обычном старте панель скрыта, PiP запускаются самостоятельно; панель открывается двойным кликом по tray-иконке или через её меню; её позиция запоминается;
- Always On Top, прозрачность, без системной рамки Windows; PiP имеют синюю рамку и скруглённые углы;
- клик по миниатюре — toggle source: видимое окно паркуется off-screen с live PiP, спрятанное/свернутое возвращается и активируется;
- свёрнутые наблюдаемые окна автоматически разворачиваются (без фокуса),
  чтобы превью оставалось живым (отключается в настройках);
- выбор окон из списка всех открытых (с фильтром);
- запоминание окон по **имени процесса + подстроке заголовка** (не по HWND) —
  после перезапуска приложения миниатюра находится и подключается автоматически;
- состояние «Окно недоступно / Ожидание...»;
- большое превью по двойному клику на миниатюре (закрывается: «✕», Esc, двойной клик,
  правый клик → «Закрыть»);
- crop — абсолютный в пикселях или **relative crop в процентах**, устойчивый к изменению размера source-window;
- правый клик по карточке: открыть окно, большое превью, collapse, crop, фильтр, click-through, пресет размера, обновить, убрать;
- иконка в системном трее (панель/карточки, Добавить окно, Профили, Настройки, Автозапуск, Выход);
- автозапуск вместе с Windows (реестр, `HKCU\...\Run`);
- опциональный детект изменений: `PrintWindow` выполняется в killable helper-процессах под
  supervisor-потоком, поэтому медленный/зависший захват чужого окна не блокирует UI; при изменении status-dot
  становится оранжевым, подаётся звук и всплывающее уведомление;
- корректная работа с несколькими мониторами: сохранённые позиции и большое превью
  привязываются к рабочей области соответствующего монитора;
- tray-иконка автоматически восстанавливается после перезапуска Explorer;
- карточки можно **пропорционально увеличивать/уменьшать за любую грань или угол** до размера рабочей области текущего монитора; старого лимита 640×520 нет, ширина сохраняется; при отпускании карточка snap-ится к краям;
- двойной клик по заголовку карточки сворачивает/разворачивает её;
- **click-through** превращает карточку в не мешающий мыши overlay; аварийное отключение у всех карточек — `Ctrl+Alt+C` или через tray;
- глобальные hotkeys: `Ctrl+Alt+A` — добавить активное окно, `Ctrl+Alt+H` — показать/скрыть панель, `Ctrl+Alt+S` — selector, `Ctrl+Alt+C` — снять click-through;
- **профили** сохраняют снимок набора окон вместе с crop, позициями, размерами, collapse/click-through;
- на первом пустом запуске автоматически открывается selector (можно отключить);
- при возврате ранее пропавшего окна показывается уведомление;
- в заголовке карточки показывается время без фокуса в минутах;
- при повторяющемся `PrintWindow` failure/black frame карточка получает предупреждение и tray-уведомление;
- detector можно отключить отдельно для конкретной карточки через её контекстное меню; спокойные окна автоматически опрашиваются реже;
- autostart запускает приложение с `--background`, без всплытия панели при входе в Windows.

## Без зависимостей

В рантайме используется только стандартная библиотека Python:

- `ctypes` — WinAPI (`user32`, `dwmapi`, `gdi32`, `shell32`): окна превью —
  нативные окна Windows, отрисовка через GDI;
- `tkinter` — только диалоги (выбор окон, настройки, crop, фильтр);
- `winreg`, `json`, `struct` — автозапуск, настройки, иконка.

Qt/PySide6 и другие библиотеки **не требуются** ни для запуска, ни для сборки exe
(PyInstaller используется только на этапе сборки).

## Запуск

Проще всего — двойной клик по `run.bat`: он запускает собранный
`dist\LookUpWindows.exe`. Или из исходников:

```powershell
python src\app.py
```

Без консольного окна:

```powershell
pythonw src\app.py
```

Требования: Windows 10/11. **Production build и релиз — только на Python 3.14 x64 с
PyInstaller 6.22.3**; это проверяется автоматически (см. «Сборка EXE» и
[docs/build.md](docs/build.md)). Исходники дополнительно совместимы с Python 3.10+ —
это только удобство разработки, и CI проверяет эту совместимость, но артефакт,
собранный на чём-то кроме 3.14, релизом быть не может.

Приложение запускается только один раз: повторный запуск тихо показывает окна
первого экземпляра и завершается — дублей в трее не будет.

## Сборка EXE

Сборка у проекта одна — **production onefile EXE**:

```bat
build-onefile.bat
```

Скрипт сначала проверяет, что toolchain совпадает с подтверждённым (CPython 3.14
**x64**, PyInstaller 6.22.3), и останавливается с ошибкой при любом несовпадении.
Сборка на другом интерпретаторе или в 32 бита даёт артефакт, который никто не
проверял. Варианта `onedir` у проекта нет: единственный production-артефакт —

```
dist\LookUpWindows.exe
```

Пока распаковка идёт, показывается `splash.png`, чтобы запуск не выглядел
зависшим.

## GitHub Releases

Готовый `LookUpWindows.exe` публикуется через GitHub Releases.
Workflow `.github/workflows/release.yml` запускается по тегу `v*` и выполняет, в
этом порядке: Python 3.14 → установка `requirements-build.txt` → проверка
toolchain → линтер и тесты → сборка onefile EXE → подтверждение, что в архиве
EXE действительно Python 3.14 → все runtime-сценарии реестра `SCENARIOS`
(`tools/runtime_smoke.py`) на готовом `dist\LookUpWindows.exe` → сборка и проверка
архива исходников → SHA-256 →
публикация. В релиз попадают **только** onefile EXE, его SHA-256, архив исходников
и его SHA-256. Ни onedir, ни служебные файлы не публикуются. При ошибке любой
проверки публикация не выполняется.

Пример для версии `2026.10.05.1`:

```powershell
git tag v2026.10.05.1
git push origin v2026.10.05.1
```

## Настройки

Из исходников настройки хранятся в `config\settings.json`. В собранной версии по умолчанию:

```text
%LOCALAPPDATA%\LookUpWindows\settings.json
```

Это позволяет запускать программу из каталогов без права записи. Старый конфиг рядом с exe
подхватывается и мигрирует автоматически. Для полностью portable-режима используйте
`LookUpWindows.exe --portable`; для собственного пути — `--config <файл>`. При сохранении
поддерживается резервная копия `settings.json.bak`.
Конфиг проверяется по схеме до применения (не `dict`/`list`, числовые поля, булевы значения — только
настоящий JSON `bool`): такой файл не используется, переименовывается в `settings.json.invalid`, а
загрузка продолжается с валидной копии.
Журнал восстановления запаркованных окон: `settings.json.park.json`. Запись появляется **до**
перемещения окна и снимается только после проверенного возврата, поэтому повреждённый журнал
(`settings.json.park.json.invalid`) переименовывается, а не читается как «обязательств нет»;
старый возраст записи не является причиной её забыть. Пока в журнале есть незакрытые записи, перед
выходом приложение подтверждает передачу отдельному процессу-guardian. Он запускается
до первой парковки и восстанавливает окна после аварийного завершения LookUp без ручного
перезапуска. Если готовность guardian не подтверждена, парковка запрещена.

Журнал пишут несколько процессов сразу (приложение, guardian, следующий старт), поэтому каждая
операция — это транзакция: под блокировкой `settings.json.park.json.lock` документ перечитывается,
меняется ровно одна запись и результат пишется атомарно. Именно это не даёт устаревшей копии
затереть более новое обязательство и делает lease (`claim`) действительно взаимоисключающим между
процессами; номер поколения документа (`revision`) служит для диагностики. Блокировка живёт в
отдельном файле намеренно: сам документ заменяется целиком, поэтому блокировка его не защищала бы,
а отдельный файл освобождается операционной системой при падении процесса.

### Кто владеет возвратом окна

Обязанность вернуть окно не привязана к одному процессу и не имеет срока годности:

- **идентичность, а не PID.** В записи лежит `ownerRunId` (случайный идентификатор запуска),
  `ownerPid` и `ownerCreated` (время создания процесса Win32). Запуск считается живым, только
  если жив PID **и** совпадает время создания, поэтому переиспользованный PID не может заблокировать
  возврат окна;
- **fencing-claim.** Claim выдаётся как пара `{поколение, токен}`: любая мутация (renew/clear/release)
  обязана предъявить оба, поэтому исполнитель, чей lease истёк, получает отказ и не может удалить
  или изменить запись, уже принадлежащую другому;
- **конечные значения.** `claimUntil`, `recordedAt` и координаты проверяются на
  `math.isfinite` и на диапазон: `Infinity`/`NaN` в lease больше не создают вечнозаблокированную
  запись, а повреждённая геометрия обнуляет только placement — сама обязанность сохраняется;
- **состояние, а не флаг.** У записи явные состояния `intent → parked` (и `stale`); удалить запись
  может только тот запуск, который её зарегистрировал, или исполнитель, который её забрал;
- **физическая проверка.** «Окно восстановлено» означает пересечение с **реальным монитором**
  (`EnumDisplayMonitors`), а не с bounding box виртуального экрана: в L-образной раскладке между
  мониторами есть пустота, и окно в ней не видно пользователю;
- **guardian без hard-lifetime.** У процесса-исполнителя нет общего дедлайна: он завершается только
  когда журнал пуст (или все оставшиеся записи принадлежат доказанно живым владельцам), либо когда
  он атомарно передал обязательства подтверждённому преемнику. Повторы идут с ограниченным
  backoff (1s → 2s → 5s → 10s → 30s → 60s → до 5 минут), логи ограничены по частоте, поэтому
  зависшее окно не съедает CPU и не превращает журнал в поток одинаковых ошибок;
- **передача владения до выхода.** При выходе приложение дожидается подтверждения guardian'а
  (включая собственный handshake) и только потом завершается; если подтверждения нет, процесс
  остаётся жив и повторяет попытку, вместо того чтобы уйти от окна, которое никто не вернёт.

Повреждённый или старый формат журнала (версия 1) мигрируется на месте под той же блокировкой в
той же транзакции: чтение новейшего состояния → миграция → атомарная запись. Старые записи не
выбрасываются, но их владелец считается неподтверждённым, а значит возврату подлежит.

```json
{
  "opacity": 0.95,
  "alwaysOnTop": true,
  "autostart": false,
  "autoRefind": true,
  "restoreMinimized": true,
  "ctrlX": null,
  "ctrlY": null,
  "changeDetection": false,
  "changeIntervalSec": 3.0,
  "changeThreshold": 0.08,
  "notifySound": true,
  "notifyWindowReturn": true,
  "hotkeysEnabled": true,
  "firstRunSelector": true,
  "windows": [
    { "process": "1cv8c.exe", "titleContains": "", "width": 280, "collapsed": false, "clickThrough": false, "detectChanges": true },
    { "process": "mstsc.exe", "titleContains": "example-server", "width": 420,
      "crop": { "mode": "relative", "x": 0.05, "y": 0.20, "width": 0.90, "height": 0.50 } }
  ],
  "profiles": {}
}
```

Позиция окна в `x`/`y` запоминается автоматически при перетаскивании.
Окно ищется по совпадению имени процесса (без учёта регистра) и вхождению
`titleContains` в заголовок. Если заголовок меняется (например, вкладка браузера),
оставьте в фильтре постоянную часть — правый клик по карточке → «Фильтр окна...».

## Проверки

В проект добавлены unit-тесты модели конфигурации, relative crop, журнала восстановления,
исполнителя восстановления и жизненного цикла процессов-детекторов:

```powershell
python -m pytest -v tests/
python -m compileall -q src
python tools/check_source_imports.py
python tools/check_build_env.py --mode dev
python -m ruff check src tools tests
```

Дополнительно `tools/runtime_smoke.py` проверяет реальное приложение (из исходников или собранный
exe): дожидается готового UI (панель + карточка), паркует чужое окно, поднимает процессы-детекторы
изменений и проверяет выполнение обязательства по возврату окна:

Полный список берётся из реестра `SCENARIOS`, без копии в документации:

```powershell
python tools/runtime_smoke.py --list-scenarios --json
python tools/runtime_smoke.py --mode exe --exe dist\LookUpWindows.exe --all
```

```powershell
python tools/runtime_smoke.py --mode source --scenario slow
python tools/runtime_smoke.py --mode exe --exe dist\LookUpWindows.exe --scenario slow
```

`LOOKUPWINDOWS_TEST_HOOKS` — переменная окружения только для тестовых сценариев
(`job_adopt_fail` принудительно отказывает в привязке helper-процессов;
`guardian_ready_stall` задерживает готовность guardian;
`guardian_fast_backoff` сжимает интервалы повторов guardian'а, чтобы сценарий lifetime
успел увидеть много попыток за секунды). Smoke-обвязка задаёт
переменную только соответствующим тестовым процессам и убирает её из обычных запусков.

Также добавлен `.github/workflows/windows-ci.yml`: на `windows-latest` выполняются compile, import smoke test, unit tests, проверка замкнутости импортов и проверка окружения сборки; `release.yml` дополнительно проверяет toolchain, собирает **onefile** exe и прогоняет по нему **все сценарии реестра** `SCENARIOS` (`tools/runtime_smoke.py`) перед публикацией. Реестр — единственный источник сценариев: workflow запускает `--all`, а тесты проверяют регистрацию каждого реализованного сценария. Любой непройденный сценарий останавливает релиз: публикации при красном recovery-наборе не происходит.

Production-сборка выполняется только на CPython 3.14 x64 с PyInstaller 6.22.3 — это
проверяется автоматически через `tools/check_build_env.py --mode release`, а состав
готового EXE дополнительно подтверждается через `tools/verify_frozen_runtime.py`.
Исходники при этом остаются совместимыми с Python 3.10+: это проверяет матрица CI как
**проверка совместимости исходников** — артефакты в ней не собираются. Подробности о
привязке версий и диагностике frozen-артефакта — в [docs/build.md](docs/build.md).

## Ограничения

- свёрнутое окно без опции «Разворачивать свёрнутые окна»: DWM может не обновлять
  содержимое — показывается заглушка;
- детект изменений использует `PrintWindow` и не работает для окон приложений,
  запущенных от администратора (если утилита запущена без прав администратора);
- детект изменений отключается на сессию, если вспомогательный процесс не удалось привязать к
  kill-on-close Job Object: непривязанный процесс — это именно тот «сирота», который пережил бы
  принудительное завершение LookUp, поэтому в этом случае детектор не запускается вовсе, а
  приложение сообщает об этом уведомлением в трее;
- во время показа рабочего стола (Win+D) авторазворачивание отслеживаемых окон временно
  подавляется, чтобы утилита не боролась с системной командой;
- утилита должна работать в той же сессии пользователя, что и наблюдаемые окна.
